## Objective

Make Logistics Flota a mobile-first operations experience for attention items, available units, active trips, recent activity, and direct departure/return actions, with responsive desktop layouts, while preserving audit history, permissions, alert semantics, and independent journey/yard lifecycles.

## Scope

- Add a Logistics dashboard and movement operations view, with direct actions and supported KPIs.
- Implement mobile cards and one-column forms; provide a dense responsive desktop table and inline filters.
- Reuse current Logistics APIs and state transitions; align backend validation only for fields explicitly required by the approved form.
- Keep overdue status derived from existing salida_at and threshold rules.
- Add loading, empty, and API error states; preserve current notifications and authorization.
- Add canonical UX documentation and supersession notes for the existing visual brief, UX spec, and EWO-006.
- Keep LOGISTICA and ADMIN_DIRECTIVO role access as currently authorized.
- Dashboard addendum: render every loaded pending-return, available-unit and active-trip row in independent vertical scroll regions; remove “Ver todos” / “Ver todas”. Preserve “Ver movimientos” and KPI links to `/flota`; keep the header action as the only solid orange button and use outline for repeated unit actions.

## Domain constraints and no-goals

- Kernel journey state and the Flota yard SALIDA/ENTRADA log remain independent.
- Do not add new persisted statuses, entities, schemas, GPS, routes, assignment desk, maintenance workflow, mileage, photo uploads, or report data.
- No editable/backdated timestamps: capture the existing server event time. Show current date/time as read-only defaults unless an existing API contract supports more.
- Do not implement vehicle return condition or maintenance integration; this requires a separate domain decision.
- No UI-only security. Backend guards remain authoritative.
- Do not invent a Reports destination; keep navigation to defined screens.

## Acceptance criteria

1. Logistics lands on a dashboard; movements are one tap away.
2. Supported overdue returns and supported incomplete records rank ahead of ordinary units; no new issue rules are invented.
3. Departure is available from dashboard/movements, only valid units can depart, and successful state changes appear without manual refresh.
4. Return is direct from the selected active/overdue row/card, closes the Logistics journey, clears the existing alert, and never creates a yard log entry.
5. At 360/390/430px the main page has no horizontal overflow, lists use readable cards, forms use one column, and actions are touch-accessible. Tablet and desktop use the existing design system and desktop table.
6. Preserve existing notifications, audit history, API guards, search, filters, Local/Foráneo, and alert thresholds.
7. Loading, empty, and API error states are clear and recoverable.
8. Relevant API tests and UI workflow checks pass; document screenshots and any deferred product gaps.

## Open-contract handling

- Existing departure API makes driver and destination optional. The UI must require the fields described by the approved spec; backend contract changes must be added only after confirming all existing callers and test coverage on this branch.
- Date/time is server event time under this EWO. Any editable historical time, return condition, maintenance action, photo upload, report, or lifecycle unification requires a separate approval.
