## Objective

Dejar que Admin ajuste y previsualice el crop de la foto principal en un editor 4:3 móvil y desktop; procesar la salida en cliente antes del guardado actual.

## Context

La ficha de unidad guarda una sola Data URL en `unidades.foto_data_url`. `UnidadForm` lee el archivo como Data URL y rechaza más de 1.5 MB; `CreateUnidadDto` aplica `@MaxLength(1_500_000)` y el parser JSON tiene límite `10mb`. Catálogo, ficha y Logística consumen el campo actual. No hay object storage. Esta ejecución conserva contrato, ownership y persistencia de ADR-014.

## Scope

- Reemplazar la lectura directa del archivo en `UnidadForm` por una etapa temporal de editor.
- Crear componente crop 4:3 con arrastre, slider zoom, pinch, restablecer, cancelar y confirmar.
- Previsualizar orientación corregida por decodificación del navegador y exportar el crop como WebP/JPEG optimizado en cliente.
- Producir máximo 1600×1200, apuntar a <1 MB y enviar el Data URL final mediante `fotoDataUrl` existente.
- Mantener el input de cámara con `capture="environment"` y selección de archivos.
- Añadir validaciones focales del procesamiento/editor sin cambiar el endpoint.

## Out of Scope

- Cambios API/schema/DB/endpoints/ADR-014, object storage o campos de imagen adicionales.
- Fotos de visitas/órdenes, galería, historial, edición de foto existente, rotación manual o recortes distintos de 4:3.
- Nuevos codecs, controles técnicos o dependencias de cropper salvo que el navegador no permita implementar criterios sin ellas.

## Domain Rules

- La foto opcional pertenece a la unidad y solo la edita Admin en catálogo (ADR-014).
- Vacío borra la foto; un Data URL válido conserva el contrato de `fotoDataUrl`.
- Las imágenes de visita permanecen separadas en `visita_fotos`.

## Dependencies

- Primitivas UI existentes de Dialog, Button, Field, Input.
- API `/unidades` existente y consumidores actuales de `fotoDataUrl`.

## Constraints

### Architecture

Mantener kernel dueño de la foto; procesamiento de UX en `web`; sin cambios de API ni schema.

### Compatibility

Conservar `fotoDataUrl` como Data URL `image/*`; asegurar JPEG fallback y compatibilidad con imágenes guardadas existentes.

### Security

No relajar `@MaxLength(1_500_000)` ni parser 10mb. Validación backend es defensa independiente.

### Performance

Procesar a máximo 1600×1200 y limitar peso; liberar object URLs y canvas temporales al cerrar.

### UX

Copy español, hit mobile ≥44px, límite del crop claramente visible y salida que coincide con previsualización.

## Assumptions, risks and data checks

- Asumido de la solicitud: WebP preferido con JPEG fallback; meta de <1 MB. El backend actual acepta ambos por `data:image/` y limita longitud de cadena.
- Los navegadores actuales aplican orientación EXIF al decodificar imágenes en canvas; confirmar con flujo mobile disponible. La salida del editor normaliza orientación al rasterizar.
- La compresión puede bajar calidad/dimensiones en imágenes ruidosas; mantener 4:3 y legibilidad, con meta de tamaño bajo límite API.
- Sin cambio de datos ni migración. Recuperación: cancelar edición preserva valor existente.
