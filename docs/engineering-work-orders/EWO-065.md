## Objective

Status colors flow from named tokens in `web/src/app/globals.css`, and a CI guard stops new literal colors.

## Context

Audit found ~40 literal hex values and Tailwind default-palette classes (orange, amber, rose, emerald, blue, sky) bypassing tokens, so token changes did not reach them.

## Scope

- Add `--status-*`, `--disabled*`, `--surface-subtle`, `--navy-hover`, `--maintenance-unknown` tokens and Tailwind mappings.
- Replace literals in `ui/badge`, `ui/button`, `ui/table`, `ui/data-table`, `ui/field`, Inicio, checks page, Logística dashboard, Unidades catálogo, `analysis.css`.
- Add `script/check-token-usage.sh` and a CI workflow.
- Add the rule to Visual QA and DESIGN_SYSTEM.

## Out of Scope

- Palette or brand change (orange `#EA7515` / navy `#24284D` unchanged; the navy/celeste/yellow trial was reviewed as a mockup and not adopted).
- Charts (`AnalysisCharts.tsx`), `maintenance-type.ts`, `SignaturePad.tsx`: JS-side colors, allowlisted.
- Renaming `--cta-hover` (documented instead; used widely).
- Sidebar grouping / information architecture (separate EWO).

## Domain Rules

None. No `api/src`, no schema, permissions or runtime behavior.

## Dependencies

None.

## Acceptance Criteria

Source of these criteria: this EWO.
- AC-1: Given a literal that already had a token-equivalent value, when replaced, then it renders the same value (Badge, Button destructive, Inicio, table, field, Unidades, analysis).
- AC-2: Given `script/check-token-usage.sh`, when a new hex literal or default-palette color class is added outside `globals.css` and the allowlist, then it exits non-zero.
- AC-3: `cd web && npm run lint` and `npm run build` pass.
- AC-4: Palette-class replacements (checks page, Logística) now follow the status tokens; small hue shifts are expected and listed in evidence.

## Testing Requirements

- `script/check-token-usage.sh`
- `cd web && npm run lint && npm run build`
- UI: `proof-ui` click-through of Inicio, checks and Logística (not yet run).
