## Objective

Every unit is created with exactly one sucursal, so it can never exist without the unit↔facility link that canonical order creation requires.

## Context

- Canonical order creation (`POST /unidades/:id/mantenimiento-ordenes`) and `GET /unit-readiness/:id` call `FacilityCalendarPort.resolve`, which returns `422 FACILITY_CONFIGURATION_REQUIRED` when the unit has no `vehicle_facilities` row. [EWO-015 evidence](../evidence/EWO-015.md): "There is no fallback facility or production seed."
- Nothing in application code writes `vehicle_facilities` or `facilities`. Tests insert them by hand. A unit created by `POST /unidades` therefore cannot get orders. This was reproduced locally with a disposable database (2026-11-07).
- User administration already validates `facilityScopes` against the `facilities` catalog (`FacilityDirectoryPort`), so the catalog must exist before users can be scoped to a sucursal.
- Business model (Owner, 2026-11-07): one facility per sucursal. "Patio" in this product only means "parked inside the sucursal" and is already the Flota physical state `EN_PATIO`; the facility is the sucursal itself. UI copy says **Sucursal**.
- Sucursales (Owner, 2026-11-07; names are exact, including "Coahuila" and "Nuevo Leon", which are route names): Matamoros, Reynosa, Coahuila, Nuevo Laredo, Tampico, CD Victoria, Monclova, Linares, Saltillo, Nuevo Leon.
- Production already has one facility: `monterrey` / "Monterrey" (`America/Mexico_City`), checked 2026-11-07, and 14 units with no mapping. Owner decision: keep `monterrey` unchanged (id and name); it is the Nuevo Leon sucursal, so users' existing `facilityScopes` keep working. Only the other 9 are seeded.

## Scope

- Seed the 9 missing sucursales into `facilities` through a controlled migration (stable ids; see Owner decisions). `monterrey` already exists and is not modified.
- `CreateUnidadDto`: required `sucursalId`; `UnidadesService.create` writes the unit and its `vehicle_facilities` row in the same transaction.
- `UpdateUnidadDto` / `update`: change of sucursal for an existing unit, ADMIN_DIRECTIVO only, with `version` increment.
- Unit read models (list / hub) expose the sucursal name.
- Web: required "Sucursal" select in `unidades/nueva` and `unidades/[id]/editar` (both already ADMIN_DIRECTIVO-only); sucursal shown read-only in the unit ficha (hub). Not added to the unit list and no sucursal filter (YAGNI), per the UX spec.
- A read of the sucursal catalog for the form (source decided at implementation; see Escalation Conditions).

## Out of Scope

- Backfill of existing units: [EWO-068](EWO-068.md).
- Per-facility timezone and removal of `facilities_timezone_check`. Deferred by the Owner (2026-11-07) to the CHECK completion work; border sucursales (Matamoros, Reynosa, Nuevo Laredo) may follow a different offset.
- Any administration screen for facilities (YAGNI). The catalog is seeded, not edited in the UI.
- Changing `TrustedActor`, OIDC mapping, order, CHECK or Flota behavior.
- Assigning `facilityScopes` to users (existing user administration).

## Domain Rules

- A unit belongs to exactly one facility; the facility is a sucursal.
- A unit cannot be created without a sucursal; the unit row and its mapping are committed atomically or not at all.
- Access scope is unchanged: a user only operates units whose facility is in their `facilityScopes`.
- Changing a unit's sucursal keeps existing behavior for CHECK winners already recorded under the previous facility (EWO-015: winner details require the CHECK's recorded facility after remapping). No new rules for in-flight CHECKs are invented here.
- No fallback facility. A missing mapping still returns `422 FACILITY_CONFIGURATION_REQUIRED`.

## Acceptance Criteria

Source: this EWO (no SPEC).
- AC-1: Given a valid payload with `sucursalId`, when the unit is created, then a `vehicle_facilities` row exists for it with that facility, in the same transaction.
- AC-2: Given a payload without `sucursalId` or with an unknown one, when the unit is created, then the API returns 400 and no unit is written.
- AC-3: Given a unit created via AC-1 and a SUPERVISOR scoped to that facility, when they create a maintenance order for it, then it is created (no 422).
- AC-4: Given a SUPERVISOR scoped to another sucursal, when they create an order for that unit, then they get `403 FACILITY_SCOPE_DENIED`.
- AC-5: Given a non-ADMIN_DIRECTIVO role, when it changes a unit's sucursal, then it is denied.
- AC-6: Given an ADMIN_DIRECTIVO changing a sucursal, then the mapping is updated, `version` increments, and the unit appears under the new facility's scope.
- AC-7: After the migration, `facilities` contains the 9 new sucursales plus the untouched `monterrey`; running it twice changes nothing.
- AC-8: The unit form requires a sucursal, the ficha shows it (or "Sin sucursal asignada"), and states match the [UX spec](../design-system/ux-unit-sucursal-v1.md); `npm run lint` and `npm run build` pass.

## Constraints

### Architecture

Reuse `Facility` / `VehicleFacility` entities and `FacilityCalendarPort`. No new Bounded Context, no schema merge, no new facility table.

### Compatibility

Existing units keep working only after EWO-068; until then they still return 422. Do not delete or relax `FACILITY_CONFIGURATION_REQUIRED`. Do not touch `/unidades` Mantenimiento hub semantics beyond adding the sucursal field.

### Security

`sucursalId` is validated server-side against `facilities`; the client list is a convenience. Only ADMIN_DIRECTIVO changes it after creation.

### Performance

One extra insert in the create transaction; read models join one small table.

### UX

Label is **Sucursal**, never "Patio". Spec UX required before implementation.
