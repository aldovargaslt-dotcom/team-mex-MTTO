## Objective

Persistir la matriz rol→permisos en el schema `auth` y exponer a ADMIN_DIRECTIVO una API para leerla y editarla con control de versión y auditoría. La matriz queda **en modo sombra**: se guarda, se audita y se lee en cada solicitud, pero **ningún endpoint ni servicio la usa todavía para decidir acceso**. Cero cambio de acceso efectivo.

## Context

EWO-067 congeló el acceso actual (163 endpoints; 135 sitios de rol en servicios) y definió el catálogo de 29 permisos con `PERMISOS_POR_ROL` equivalente a los `@Roles`. ADR-021 fija el patrón: tabla en `auth`, versión de registro, advisory lock, auditoría antes/después atómica, sin caché de roles, migración separada y no automática (`auth:migration:up`; `synchronize`/`dropSchema` en `false`). El directorio de usuarios solo es autoritativo con `AUTH_ACTOR_STORE=DATABASE`; con `CONFIG` no existe persistencia de accesos.

## Scope

1. **Migración Auth** (aditiva, reversible, con `down`): tablas `auth.role_permissions` (rol, permiso, otorgado) y `auth.role_permissions_audit` (rol, actor, acción, antes/después, fecha) + versión por rol. Siembra con **literal fijo** equivalente a `PERMISOS_POR_ROL` de EWO-067 (no importa constantes mutables); una prueba exige igualdad literal ↔ constante.
2. **Servicio de matriz**: lectura de la matriz vigente en cada solicitud (sin caché de rol), escritura transaccional bajo advisory lock propio (distinto de 825025), `expectedVersion`, auditoría atómica.
3. **API** solo ADMIN con identidad confiable: `GET /admin/permissions` (catálogo + matriz + versión + `enforced:false`) y `PUT /admin/permissions/roles/:rol` (conjunto completo de permisos del rol + `expectedVersion` + motivo).
4. **Invariantes**: permisos y roles desconocidos se rechazan; ADMIN_DIRECTIVO siempre conserva `usuarios.administrar` (AC-P07); edición con versión obsoleta → 409 (AC-P06).
5. **Fallo cerrado** (OQ-5): si la matriz no se puede leer, `GET`/`PUT` devuelven error claro y no se concede nada; solo ADMIN conserva `usuarios.administrar` como mínimo seguro.
6. **Modo CONFIG**: la matriz expuesta es la constante por defecto, **solo lectura** (PUT → 409 explicativo). Ver O-1.

## Out of Scope

- Hacer que cualquier guard, `@Roles` o `authorize(...)` consulte la matriz (EWO-069+).
- Migrar los 42 endpoints sin `@Roles` o los 135 sitios de servicio.
- Crear roles nuevos (Fase 2), pantalla de administración, o configurar/recortar Mecánico o cualquier rol.
- Cambios a `facilityScopes`, OIDC, `VisitaCerrada`, `user_audit` o a la tabla `auth.users`.
- Ejecutar migraciones en producción o activar `AUTH_ACTOR_STORE=DATABASE`.

## Domain Rules

- Equivalencia primero: tras sembrar, la matriz de cada rol es idéntica a `PERMISOS_POR_ROL`.
- Fallo cerrado: permiso desconocido, rol desconocido o matriz ilegible ⇒ denegar/rechazar, nunca conceder.
- Cada cambio audita quién, cuándo, antes/después y motivo; no hay UPDATE silencioso.
- Sombra: editar la matriz **no** cambia el acceso real mientras no exista enforcement; la API lo declara (`enforced:false`) para evitar falsa sensación de control.

## Constraints

### Architecture
Todo dentro de `auth` (ADR-002): sin FKs ni JOINs a otros schemas. Migración Auth separada del historial CHECK; no se ejecuta automáticamente.
### Compatibility
Sin cambios de contrato en endpoints existentes. Endpoints nuevos solo bajo `/admin/permissions`. Un despliegue sin ejecutar la migración no puede romper el arranque (la matriz no se usa para decidir acceso).
### Security
Solo ADMIN con identidad confiable; sin headers ni claims de proveedor como fuente de permiso; sin datos personales nuevos; auditoría sin tokens.
### Performance
Una lectura pequeña por solicitud a la API de matriz; sin impacto en el resto de rutas (sin enforcement).
### UX
No aplica.
