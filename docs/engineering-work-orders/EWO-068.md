## Objective

Give every already existing unit the `vehicle_facilities` row for its sucursal, so canonical orders can be created and listed for it.

## Context

- Units created before [EWO-067](EWO-067.md) have no `vehicle_facilities` row and fail with `422 FACILITY_CONFIGURATION_REQUIRED`.
- Facility mappings are explicit owner configuration; there is no default facility (EWO-015 evidence). The backfill must therefore use real data from the Owner, never a guess.
- Sucursales: Matamoros, Reynosa, Coahuila, Nuevo Laredo, Tampico, CD Victoria, Monclova, Linares, Saltillo, Nuevo Leon (exact names).

## Scope

- A reviewed, idempotent script that inserts `vehicle_facilities(unidad_id, facility_id, version=1)` from an Owner-supplied list `numeroInterno → sucursal`.
- A dry-run mode that reports: units to be mapped, units already mapped, units in the list that do not exist, units missing from the list, unknown sucursal names.
- Pre/post counts as evidence.

## Out of Scope

- Creating or editing facilities (EWO-067 seeds them).
- Defaulting unmapped units to any sucursal.
- Changing units that already have a mapping.
- Assigning `facilityScopes` to users.
- Timezone handling (deferred by the Owner).

## Domain Rules

- A unit gets exactly one facility, taken only from the Owner's list.
- Unlisted units are reported and left unmapped; the script never infers a sucursal.
- Existing mappings are never overwritten.
- Forward recovery only: configuration is not deleted to roll back (EWO-015).

## Dependencies

- EWO-067 seeded `facilities` (the script fails if a sucursal id does not exist).
- Owner-supplied mapping file, kept out of the repository if it holds anything sensitive.
- A verified database backup and the Owner's go-ahead to run on production.

## Acceptance Criteria

Source: this EWO.
- AC-1: Given a mapping list and a disposable database, when the dry run executes, then it writes nothing and prints the five report categories above.
- AC-2: Given the same list, when the script runs, then every listed existing unit has exactly one mapping to the listed facility.
- AC-3: Given the script already ran, when it runs again, then no row changes.
- AC-4: Given a unit that already had a mapping, when the script runs, then that mapping is unchanged.
- AC-5: Given an unknown sucursal in the list, when the script runs, then it aborts before writing anything.
- AC-6: After AC-2, a SUPERVISOR scoped to the unit's facility can create a maintenance order for a backfilled unit, and `GET /unit-readiness/:id` responds 200.

## Testing Requirements

- Fixture test on a disposable database for AC-1…AC-6 (units created without a mapping, then backfilled).
- Commands (disposable only; `EWO_DISPOSABLE_DB=true`, `DATABASE_URL` cleared):
  - `cd api && npm run build && npm run test:e2e`
- Production run (after approval): dry run first; record counts before and after in evidence.

## Constraints

### Architecture

Reuse `VehicleFacility`; no new tables. A one-off script, not an application feature.

### Compatibility

Does not alter units, orders, CHECKs or users.

### Security

Runs in one transaction. Requires the explicit target database name, in the style of the existing controlled runners, to avoid hitting the wrong database. No secrets in the repository.

### Performance

Small data set (units only).

### UX

None.
