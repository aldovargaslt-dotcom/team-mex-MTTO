## Objective

A developer or agent can start the whole app locally with one command and use every role's screens: no `401` on endpoints that need a verified actor, and demo sucursales and units available. Nothing changes outside `NODE_ENV=development`.

## Context

Found during [EWO-067](../evidence/EWO-067.md):
- **Identity.** In local development the web client sends only `X-Role`, but order, readiness and check endpoints require a verified actor. They return `401`, the client dispatches `team-mex-session-expired` and the app returns to the role picker. The API already has `AUTH_MODE=DEVELOPMENT_STUB` with `AUTH_STUB_ACTORS` (token → actor), refused outside `development`/`test` by `assertIdentityConfiguration`. Nothing sends the token: the dev branch of `web/src/app/backend/[...path]/route.ts` forwards `authorization` only if the browser already sent one.
- **Sucursales.** The 9 sucursales are seeded by a migration that only the release runner applies. A database created with `synchronize` has none, and the demo seed creates no facilities. Since EWO-067 the unit form requires a sucursal, so a fresh local database cannot create a unit.
- **Startup.** Starting needs Postgres, env vars for the stub actors and two terminals; the steps are spread over `.cursor/start.sh`, `.cursor/environment.json` and the README.
- The existing rule that the browser's `X-Role`/`X-User-Id` headers are never an identity source for the API stays: the actor and its roles and facilities come from server-side configuration.

## Scope

1. **Dev identity (web proxy).** In `legacyDevelopment()` mode only, when the browser sends no `Authorization`, the proxy adds `Authorization: Bearer <WEB_DEV_TOKEN_PREFIX><role>` from a server-side environment variable (for example `dev-SUPERVISOR`). The role is the one selected in the role picker.
2. **Dev actors (API).** A documented `AUTH_STUB_ACTORS` for the four roles (`dev-SUPERVISOR`, `dev-ADMIN_DIRECTIVO`, `dev-LOGISTICA`, `dev-MECANICO`) with the dev facility scopes, supplied by the launch script and `api/.env.example`, never by code defaults.
3. **Dev facilities (API seed).** When `NODE_ENV=development` only, the demo seed ensures the 10 sucursales (`monterrey` plus the 9 from EWO-067) and maps the demo units to `monterrey`. Idempotent; skipped in any other environment.
4. **One command.** `script/dev-local.sh`: waits for Postgres, starts the API with the dev actors and the web with `API_URL`, prints the URLs. `.cursor/environment.json` terminals and the README use it.

## Out of Scope

- Any change to production authentication, OIDC, `TrustedActor`, `AuthenticationPort` or the actor directory.
- Browser or screenshot tooling in the repository (see Owner decision 3).
- Real facilities or units in production, or any seed that runs outside development.
- Adding Playwright or another test framework to `web/`.
- The deployed Railway/Vercel environments.
- Per-facility timezone (deferred by the Owner to the CHECK work).

## Domain Rules

- Identity for the API always comes from server-side configuration; the browser only selects which configured dev actor to use, and only in `NODE_ENV=development`.
- Production behavior is unchanged: the stub is refused outside `development`/`test`, and the seed does not create facilities in production ("no production facility seeds", EWO-015).
- Dev tokens and actors carry no extra privilege beyond the role and facilities they are configured with.

## Acceptance Criteria

Source: this EWO.
- AC-1: Given a fresh local database and the one command, when each role is chosen in the role picker, then orders, unit readiness and checks load with no `401` and the app does not return to the role picker.
- AC-2: Given `NODE_ENV=development`, when the API starts on a fresh database, then the 10 sucursales exist and the demo units are mapped to `monterrey`; starting again changes nothing.
- AC-3: Given a fresh local database, when an administrator creates a unit from the form, then it succeeds and a supervisor of that sucursal can create an order for it.
- AC-4: Given `NODE_ENV=production`, when the seed runs, then no facility is created (automated test).
- AC-5: Given `NODE_ENV=production`, when `DEVELOPMENT_STUB` is configured, then startup is refused (existing behavior stays covered).
- AC-6: Given `NODE_ENV=production`, then the web proxy never adds a dev token and still requires the session cookie (check by code and test where practical).
- AC-7: The README and `.cursor/environment.json` describe the single path; no third path is introduced.
- AC-8: `cd api && npm test && npm run test:e2e`, `cd web && npm run lint && npm run build` pass.

## Constraints

### Architecture
No new module. Reuse the stub port, the seed service and the proxy route.

### Compatibility
Behavior outside `NODE_ENV=development` is identical. Existing e2e fixtures must not need changes.

### Security
Dev token prefix and actors live in server-side environment only, never in the browser bundle and never in code defaults. Guard both the proxy and the seed on `NODE_ENV === 'development'`. The security-sensitive part is the proxy injection; it needs the Owner's confirmation (Decision 1).

### Performance
Negligible.

## Assumptions, risks and data checks

- Confirmed (2026-11-07): without a token, `/unit-readiness` returns 401 in local development and the app returns to the role picker; with a stub actor and `Authorization: Bearer` it works.
- Risk: a dev token path leaking into production. Mitigation: guard on `NODE_ENV === 'development'` plus tests and code review.
- Risk: the dev seed touching real data. Mitigation: development only, idempotent, never on a database whose name is not the local dev one.
- Confirm a disposable test database and resolved target (including `DATABASE_URL`) before any destructive test.
