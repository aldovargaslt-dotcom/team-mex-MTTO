## Objective

Que la interfaz muestre u oculte las acciones y los importes de Inventario y costos según los permisos efectivos que el **servidor** informa, en lugar de comparar roles fijos. Con la matriz sembrada, lo que ve cada rol no cambia (salvo lo que decida D-5). Es el requisito previo para poder editar permisos de inventario/costos en un entorno real sin dejar botones que fallen o importes visibles.

## Context

- La web conoce al usuario por `GET /api/auth/session` → `identity()` → API `GET /auth/me`, que hoy devuelve el actor sin permisos. `RoleProvider` (`lib/role.tsx`) expone `role`, `roles`, `isAdmin`…; ~123 comparaciones de rol repartidas por componentes; `RoleGate` recibe listas de roles.
- Componentes del área con lógica de rol: `app/inventario/layout.tsx` (`RoleGate`), `InventorySectionMenu`, `InventarioCatalogo`, `app/inventario/stock/page.tsx`, `InventoryCostPanel` (`role === "ADMIN_DIRECTIVO"` para abrir valoración y para completar/corregir), `ApplicationNavigation` (entrada Inventario por rol) y, a verificar, `UnitRefactionCosts` y las vistas de análisis que muestran importes de refacciones.
- Modo desarrollo (`legacyDevelopment`): no hay actor en la sesión; los roles se eligen de una lista y se envía `X-Role`.
- El 401 dispara `team-mex-session-expired`; un 403 no tiene tratamiento global (correcto: no debe cerrar sesión).
- **Desalineación conocida UI/API:** la UI limita completar/corregir/abrir valoración a ADMIN; el API permite completar y corregir a SUPERVISOR y solo restringe la apertura (ver EWO-070, hallazgos 1 y 2). Alinear la UI a permisos expone esa diferencia: depende de D-5.

## Scope

1. **API, cambio aditivo en `GET /auth/me`**: agregar `permissions: string[]` (permisos **efectivos** del actor: unión de sus roles) y `enforcedAreas: string[]`. Los permisos de un área con enforcement activo salen de la matriz vigente; los de áreas sin enforcement salen de la equivalencia por roles (constantes, probadas equivalentes a `@Roles`), de modo que la lista siempre refleje lo que el servidor **realmente** decidirá. Sin cambiar los campos existentes.
2. **Web, sesión**: `identity()` y el tipo `Identity` aceptan los campos nuevos (tolerando su ausencia); `RoleProvider` expone `permissions`, `can(permiso)` y recarga de sesión.
3. **`PermissionGate`** (y helper `can`) junto a `RoleGate`; migrar el área piloto: entrada de navegación Inventario, layout/secciones de inventario, `InventarioCatalogo`, página de existencias, `InventoryCostPanel` (acciones y columnas/valores de importes) y cualquier superficie del área que muestre importes. Dónde aparecen importes fuera del área se **inventaría** y se documenta (no se migra aquí).
4. **Sin permiso**: ocultar la acción (criterio actual del producto); acceso directo por URL sin permiso → pantalla neutral «No tienes permiso para ver esto» con salida a inicio; importes sin `costos.ver` no se renderizan (ni valores ni columnas ni totales ni gráficas derivadas).
5. **Frescura**: la UI recarga permisos al recuperar el foco, al recibir un 403 del área y manualmente; un 403 por permiso muestra un mensaje claro y refresca, **sin** cerrar sesión.
6. **Modo desarrollo**: respaldo con un mapa estático generado desde la fuente única (`PERMISOS_POR_ROL`) y una prueba en la API que falla si el archivo de la web se desincroniza.
7. **UX addendum y revisión**: documento breve de comportamiento de visibilidad por permiso y cadena de revisión de UI del repositorio.

## Out of Scope

- Cualquier cambio de enforcement en el API (EWO-070) o de matriz; la decisión D-5 solo se refleja aquí.
- Otras áreas de la UI (CHECK, Flota, Logística, Andon, Salud, configuración), los ~120 usos de rol restantes.
- Pantalla de administración de la matriz; roles nuevos; configurar Mecánico u otro rol.
- Ocultar importes en áreas que los muestran por otra vía de API (p. ej. análisis de mantenimiento): se documenta como límite y queda para EWOs de esas áreas, porque ocultarlos solo en la UI no cumpliría AC-P09 (el servidor debe negarlos).
- Rediseño visual, nuevos componentes de layout o cambios de tokens.

## Domain Rules

- El servidor es la autoridad (SPEC-AUTH-003 F-05): la UI refleja, nunca concede; un permiso visible en la UI no implica acceso real.
- Equivalencia primero: con la matriz sembrada, la lista de permisos devuelta por `/auth/me` produce las mismas acciones visibles que hoy para SUPERVISOR y ADMIN_DIRECTIVO, salvo la diferencia declarada en D-5.
- Sin permiso `costos.ver` no se muestra ningún importe; ausencia de dato ≠ cero (SPEC-INV-001).
- Roles y permisos del actor vienen del servidor; no se leen de `localStorage` ni de claims.

## Acceptance Criteria

Canónicos en SPEC-AUTH-003: **AC-P09** (sin permiso financiero no se revelan importes ni se aceptan cambios — aquí la parte de UI, con el servidor como autoridad), **AC-P08** (la UI ve el cambio de matriz tras recargar, sin reinicio) y sin regresión de P01–P07, P10–P14.

Criterios propios (fuente: este EWO):
- **U-01** Dado un actor autenticado, `GET /auth/me` devuelve los campos actuales sin cambios más `permissions` y `enforcedAreas`; clientes que ignoran los nuevos campos siguen funcionando.
- **U-02** Dada cualquier combinación de roles del actor, matriz (sembrada o editada) y flag de enforcement, `permissions` coincide exactamente con lo que el servidor decidiría para las operaciones del área (prueba de consistencia contra el guard).
- **U-03** Dado SUPERVISOR o ADMIN_DIRECTIVO con la matriz sembrada, la UI del área muestra las mismas acciones que antes (salvo D-5), verificado con capturas antes/después.
- **U-04** Dado un rol sin una acción, la UI no la muestra; dado un rol sin `costos.ver`, no se renderiza ningún importe, columna ni total en el área.
- **U-05** Dado un 403 por permiso (p. ej. cambió la matriz durante la sesión), la UI muestra un mensaje claro, recarga permisos y conserva la sesión.
- **U-06** Dado el acceso por URL a una sección sin permiso, aparece la pantalla neutral y no se hacen llamadas de datos de esa sección.
- **U-07** Dado modo desarrollo, el respaldo estático produce las mismas acciones que la lista del servidor para cada rol, y la prueba de sincronización falla ante desfase.
- **U-08** Dados 390 px, teclado y zoom 200 %, las superficies tocadas siguen siendo accesibles (targets ≥ 44 px, sin scroll horizontal de página, foco coherente).
- **U-09** Dada la cadena de revisión de UI del repositorio, existen `better-ui`, `proof-ui` (capturas reales, sin Playwright) y revisión independiente `ux-auditor` sin hallazgos P0–P2 abiertos.

## Constraints

### Architecture
API: único cambio en el servicio de identidad/`/auth/me` y un cálculo de permisos efectivos reutilizando `PermissionMatrixService` y las constantes de EWO-067; sin tablas. Web: Next.js App Router + shadcn/Tailwind (ADR-003); sin duplicar la lógica de decisión (el servidor entrega la lista).
### Compatibility
Cambio aditivo en `/auth/me`; `identity()` valida la forma existente y tolera ausencia de los campos nuevos; despliegues desfasados API↔web no deben romper la sesión (si faltan `permissions`, la UI cae al comportamiento por rol actual).
### Security
La UI no es frontera de seguridad; no exponer la matriz completa ni otros usuarios; `Cache-Control: no-store` conservado; sin PII nueva.
### Performance
Un cálculo ligero por solicitud a `/auth/me` (una lectura de matriz en modo `DATABASE`); la sesión ya se pide al cargar.
### UX
Seguir el contrato visual y APPLICATION_NAVIGATION (AppShell + ApplicationNavigation); revisar varias rutas y roles; textos en español.
