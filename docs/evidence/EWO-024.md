# Evidencia EWO-024 — Autenticación web OIDC

Autorización: usuario solicita implementar autenticación web y preparar OpenID
Connect sin proveedor existente. SPEC-AUTH-001 / ADR-018 / UX auth-web-v1.
Conservados los cambios EWO-023 y baseline `ddd1ac8`, sin commit ni PR.

## Implementación

API: adapter jose JWT RS256/JWKS, issuer/audience/sub/iat/exp, mapping autorizado
server-side de nombre/roles/patios, sin SYSTEM interactivo. OIDC protege también
endpoints legacy; identidad GET `/auth/me` con no-store. No permisos de dominio
nuevos ni cambios de DB.

Web: login Authorization Code + PKCE S256; state/nonce, firma/issuer/audience,
azp/at_hash, vigencia y coincidencia de subject entre ID token y actor API.
Sesión JWE A256GCM HttpOnly/Secure/SameSite=Lax, máximo una hora/token expiry,
sin token/identidad aleatoria en localStorage. Proxy de servidor elimina headers
cliente de identidad, agrega Bearer, preserva binarios y exige Origin autorizado
en escrituras; no fallback a backend producción. UI recibe roles reales y
logout/401 limpian sesión/identidad y ocultan contenido protegido.

## Qué prueban los fixtures

Tokens realmente firmados; TLS verificado por los procesos de aplicación con CA
de prueba añadida, sin desactivar TLS de app. Chrome ignora únicamente el error
de certificado local para captura. Adapter real API consulta JWKS HTTPS del
fixture; ID token, access token y sesión cifrada reales del protocolo de prueba.

Negativos: state inválido, nonce incorrecto, at_hash incorrecto, code replay,
token vencido, usuario no provisionado, cookie falsificada/vencida, spoofing de
X-Role/X-User-Id/Authorization, CSRF, pérdida de autorización y API indisponible.
Binario privado preservado byte por byte; cookie eliminada por logout/401.
Pruebas unitarias también cubren firma falsa, algoritmo no permitido,
issuer/audience inválidos, iat/nbf futuro, claims requeridos y JWKS indisponible.

El servidor de dominio del walkthrough es sintético (Mi trabajo vacío y badge).
No acredita CHECK con persistencia real bajo un proveedor real ni permisos nuevos
para mantenimiento. Ese recorrido se debe completar en staging con API/DB/storage
configurados; los E2E existentes de CHECK/persistencia pasan por separado.

Recorrido: `/` → login/callback → rol MECANICO del servidor → Mi trabajo vacío →
logout desktop → volver a ruta protegida sin sesión → login/móvil → menú y logout
visible → error/loading de consulta sesión → login → revocación fixture API →
401 → inicio con sesión vencida. Solo error/loading de consulta sesión y fallo de logout se
interceptan para capturas; login/callback, JWT/JWE, proxy y rechazo 401 no se mockean
en el navegador. Roboto cargada y ausencia de identidad aleatoria comprobadas.

La cuenta multirrol es otro subject sintético autorizado server-side con MECANICO
+ SUPERVISOR, sin Admin. Login/tokens e identidad son reales del protocolo de
fixture, no grant del navegador. Se cliquea «Elegir rol» en desktop y menú móvil
sin terminar sesión. Fallo de logout devuelve 503 interceptado; el navegador
confirma que la sesión sigue autenticada y el mensaje es español controlado.
Error de sesión usa 503 HTML, reproduciendo response.json fallido sin exponer
«Unexpected token»/«Failed to fetch» al usuario.

## Correcciones de revisión independiente

Primer pase ux-auditor: no OK por propagación de error.message en consulta sesión
y falta de proof multirrol/logout fallido. Corregido a mensaje español fijo,
comprobados los dos roles autorizados sin Admin, logout fallido conserva sesión,
y añadidas seis capturas. El acceso «Elegir rol» queda condicionado a más de un
rol autorizado y conserva la sesión; no es cambio libre de privilegios.
Segundo pase encontró una captura de Sheet durante animación; se recapturó sólo
ese menú tras terminar animaciones y verificar bounds de todos los controles.
Veredicto final independiente ux-auditor: OK visual acotado al incremento local
EWO-024. Las 21 capturas no muestran regresiones nuevas; cierre y ambos controles
del menú móvil quedan completos dentro del viewport. No acredita proveedor real,
staging ni permisos de Mantenimiento.

No se modificó el script build del repo para ocultar el fallo de fuentes:
Turbopack FAIL es una limitación de verificación distinta de la integración OIDC.
El build estándar final con tipos/lint y Roboto pasa.

## Pendientes operativos / límites

Proveedor debe cumplir el contrato de tokens/scopes y client_secret_post; configurar
Vercel y API con secreto/callback/origin/issuer/audience/JWKS y subjects/patios reales.
Mapping por configuración requiere restart para revocar/cambiar permisos; no hay
admin de cuentas, refresh, revocación central ni logout global del proveedor.
Cookie tiene límite de tamaño; token grande no establece sesión.
Guía completa: `docs/design/auth-web-staging.md`. Autenticación no habilita aún
los permisos de work orders, preventivos, tickets ni formularios pendientes.
