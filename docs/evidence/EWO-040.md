## Rollout and data safety

1. Back up and rehearse against a staging copy; verify database identity and existing quantities. Keep `INVENTORY_COSTS_ENABLED=false` during preparation.
2. Build API. Run `DB_SYNCHRONIZE=false DB_DROP_SCHEMA=false INVENTORY_MIGRATION_DATABASE=<verified-name> npm --prefix api run inventory:migration:up` with the intended database connection. Runner verifies current_database, serializes migrations using a dedicated advisory-lock connection and records a dedicated migration ledger. No startup schema synchronization is enabled.
3. Enable `INVENTORY_COSTS_ENABLED=true` when API+web are released together. Production defaults this flag off; financial endpoints return503 until activated. New financial receipt UI requires activation. Coordinate release rather than leaving that UI active with costs off.
4. Admin verifies current quantity and net valuation before known weighted costing of legacy stock. Legacy consumption stays unknown until explicit audited regularization. No historical prices are inferred. A quantity change while costing is disabled invalidates stale valuation.
5. Preserve cost tables on rollback. Do not run down to delete finance history. Disable writes/feature and redeploy a compatible version if rollback is required.

No vendor financial returns, warranty/exchanges, freight/discount allocation, acquisition value, cost/km or total maintenance cost were added. Document status and financial state are independent. Recent item history is limited to100 operations; scoped document/unit reads use their full matching operation set. Period aggregation is currently client-side over the authorized unit read, suitable for initial scope; larger histories should move aggregation server-side. Threshold notifications retain the existing publisher and log delivery failures; a durable financial-notification outbox was not introduced.

## Implemented contract mapping

The first implementation consolidates conceptual `cost_revisions` and `consumption_costs` into `cost_operations` with immutable snapshots and appended revision JSON (rather than extra tables). It exposes `/inventario/costos/consumos` with authorized raw operations; the web derives coverage and local-date periods instead of the proposed server aggregate DTO/paginated report. Validation follows existing Nest400 conventions rather than introducing422. These are implementation differences from the proposed technical contract, not claims that its exact endpoint/DTO shape shipped. Canonical domain rules remain enforced; large-history aggregation and audit-history browsing are follow-up scalability/UI work.
