## How to run it (Owner, on production, after approval)

Build first (`npm run build` in `api`), then from `api`:

```bash
UNIT_SUCURSAL_BACKFILL_DATABASE=<exact database name> DB_SYNCHRONIZE=false DB_DROP_SCHEMA=false \
  node dist/db/run-unit-sucursal-backfill.js --facility=monterrey
```

That is a dry run: it writes nothing and prints `facilityExists`, `totalUnits`, `alreadyMapped` and the list `toMap`. Add `--apply` only after reviewing the report and confirming a backup. Re-run the count of unmapped units just before.

## Acceptance Criteria

### AC-1 — PASS
Dry run writes nothing (`vehicle_facilities` count stays 0) and reports `facilityExists`, `totalUnits`, `alreadyMapped`, `toMap`. With a facility that does not exist the dry run reports `facilityExists: false` and still writes nothing. Compiled runner on a local dev database: `DRY_RUN`, 13 units, 2 already mapped, 11 to map, 0 applied, count unchanged.

### AC-2 — PASS
Apply maps every unmapped unit to the target facility with `version` 1 (e2e).

### AC-3 — PASS
A second apply returns `applied: 0`, empty `toMap`, and the table is identical (e2e).

### AC-4 — PASS
A unit already mapped to another facility keeps its facility and version (e2e: `saltillo`, version 4).

### AC-5 — PASS
Unknown facility with `--apply` aborts with `SUCURSAL_NOT_FOUND` and writes nothing (e2e, and compiled runner). Missing `--facility`, missing `DB_SYNCHRONIZE=false`/`DB_DROP_SCHEMA=false`, and a wrong `UNIT_SUCURSAL_BACKFILL_DATABASE` each stop the runner before connecting to any data (compiled runner).

### AC-6 — PASS
After the backfill a supervisor scoped to the sucursal gets 200 from `GET /unit-readiness/:id` and 201 creating a maintenance order (e2e).

## Domain Consistency

No default sucursal: the facility id is a required argument. Existing mappings are never overwritten. Forward recovery only; nothing is deleted.

## Architecture / ADR Consistency

Reuses `vehicle_facilities`; no new table, no entity change. A one-off runner in the style of the other controlled runners. The whole backfill runs in one transaction.

## Scope Review

Within scope. Facilities, users and their `facilityScopes` are not touched.

## Deviations

None.

## Known Limitations

- **Not run on production.** Preconditions: a verified backup, a check that users have `monterrey` in their `facilityScopes`, a fresh count of unmapped units, and the Owner's explicit approval. The Owner's last check (2026-11-07) was 14 units, 0 mapped, one facility `monterrey`.
- The runner needs the exact database name in `UNIT_SUCURSAL_BACKFILL_DATABASE`; it does not accept a URL as a substitute.
- Users must already have `monterrey` in their `facilityScopes`, or they get `403 FACILITY_SCOPE_DENIED` after the backfill.
- A visible symptom to confirm success: the red "No pudimos confirmar la operabilidad" panel in the ficha of a unit without a sucursal should disappear after the backfill (see EWO-067 evidence).
